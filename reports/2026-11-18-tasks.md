# Результаты 18.11.2026

## 1. Обогащение и обновление

Уточнено требование: сохранять все объявления, включая снятые с продажи.
Снятые помечаются статусом, строки не удаляются.
В проверенной базе прогона 4 — 739 544 объявления, из них 456 299 активных
(текущий срез, не полный объём источника).

Реализован контроллер двух проходов: первые 12 страниц примерно каждые
10 минут, между ними архив порциями до 120 страниц. Полное обновление архива —
через сутки после завершения предыдущего. Курсоры, наблюдения и расписание
хранятся в PostgreSQL. Переключение режимов не сбрасывает архив.
Свежие цена и статус не перекрываются старой подробной карточкой;
характеристики и дополнительные фото из карточки сохраняются.

Живая проверка recent: **12 запросов, 576 строк, 1 новое объявление,
9,342 с, все ответы 200**. Это помогает быстро замечать новинки, но ограниченное
окно не доказывает полноту, поскольку сортировка учитывает качество карточек.

Обогащение проверено на 3 реальных HTML-карточках с недостающими полями.
Все ответили 200; затрачено 5,638 с, дополнительных проверенных характеристик — 0.
Небольшая проба не оправдывает массовый обход отдельных карточек.
Рекомендация: сначала актуальный список, затем целевое обогащение только
того поля, для которого на выборке доказана польза дополнительного запроса.
Существующая очередь карточек доступна вручную; массовый обход не включён.
Сырые результаты: `2026-11-18-enrichment.json`.

## 2. Собственное API

Работает в Docker: http://127.0.0.1:8766/docs.
JWT HS256 с issuer/audience/expiration, scrypt-пароли с солью, отзыв токенов
при смене пароля/отключении пользователя. Секреты в игнорируемых файлах 0600.
Авторизация закрыта без настройки секрета. Пользователи создаются через CLI.

Каталог GET /cars или POST /cars/search; единичная карточка /cars/{id};
список прогонов /runs; описание полей /fields.
Пагинация 1–1000 записей, подписанный курсор, без глубокого OFFSET.
Все нормализованные поля и исходные JSON доступны для фильтрации.
JSON-пути и значения передаются параметрами SQL; выражения не исполняются.
API читает локальную БД, не делает запросов к источнику.

Фактическая проверка контейнера: Swagger/OpenAPI — 200;
1000 объявлений — **0,052 с**, 100 объявлений с исходными JSON — **0,071 с**.
Это отдельные локальные замеры, не нагрузочный тест.
Для произвольных JSON-фильтров без индексов действуют ограничения времени;
пагинация по обновляющейся базе не является замороженным снимком.
Подробности и запуск: `docs/catalog-api.md`.

## 3. Скорость

Свежая проба SATAuto, Китай, 30 страниц в каждом варианте:

| Режим | Фактических цепочек | Запросов | Полученных строк | Секунд | Время БД |
| --- | ---: | ---: | ---: | ---: | ---: |
| workers=3, одна страна | 1 | 30 | 1440 | 36,241 | 2,292 |
| workers=6, страна по 3 диапазонам лет | 3 | 30 | 1440 | 14,763 | 1,494 |

Все 60 ответов — 200. Получение страниц во втором варианте быстрее в **2,45 раза**
при том же числе запросов. Второй замер использовал ту же временную базу:
в нём 464 новых строки, остальные уже были в первом варианте.
Это сравнение времени получения страниц, а не 2,45-кратный рост новых ID.
Часть разницы времени БД объясняется insert против update/неизменившихся строк.
Исходные данные: `2026-11-18-speed.json`.

Разделение по годам уже было в предыдущем сборщике. Нового ускорения
полного обхода относительно его прежних шести запросов здесь не доказано.
Изменён режим поддержки актуальности, чтобы не ждать полного прохода.
В долгом фоновом обходе по-прежнему наблюдаются 502, включая исчерпание
двух повторов; контроллер продолжает с сохранённой позиции после паузы.
Срез последней порции: `2026-11-18-sync.json` (он может содержать временную ошибку,
а не завершение всего каталога).

При лимите источника 48 машин на миллион нужно минимум **20 834 полезных
запроса**, плюс последние страницы, проверки и повторы. По короткому лучшему
замеру миллион соответствовал бы примерно 2,85 ч, но это арифметическая
нижняя оценка без сбоев и неполных страниц, не обещание длительности полного сбора.
Размер всего текущего источника точно не установлен, завершение не заявлено.

Сессия без cookies уже работает. Источниковый курсор не нужно генерировать
самостоятельно: он относится к версии серверного индекса; один курсор —
последовательная цепочка. Дополнительные одинаковые парсеры повторят данные.
Сторонний сервер пока не тестировался: без доступа и замеров из выбранного
дата-центра нельзя обещать прирост. Его польза — возможная более короткая сеть
и работа 24/7. Сначала нужен сравнительный замер, затем распределённая очередь,
если появится доказанный выигрыш. Лимит 48 и ошибки источника сервер не отменит.

## Проверки и состояние

36 автоматических тестов прошли, включая JWT, пагинацию всех статусов,
фильтры/инъекции, отзыв токенов, независимость recent/архив, возобновление,
409, 429, 502/503, backoff, сохранение статуса и обогащённых характеристик.
После уточнения слияния фото повторно проверен соответствующий тест.
Тесты используют временную отдельную БД и не останавливают живой сборщик.

API и parser запущены в Docker; PostgreSQL и прежний dashboard работают.
Обычная сборка остановилась на обращении к Docker Hub за базовым образом.
Для локального запуска использован уже имеющийся образ: установлены
закреплённые зависимости и скопирован текущий код, результат проверен контейнерами.
Обычный Dockerfile с новыми requirements сохранён для следующей сборки.
На удалённый сервер ничего не развёрнуто. Коммиты и push не выполнялись.
